# MoviePilot 洗版两次插件

MoviePilot V2 插件：让订阅里的**每一集最多下载两次**——第一次只下本批候选里**优先级最低**的一档（出得最快的那版），第二次只升到**本批最高档**（当时能拿到的最好那版），之后不再洗版。不需要配置任何档位。

本实现使用 V2 导入路径：`app.plugins` / `app.core.event` / `app.log`，订阅读写走 `app.db.subscribe_oper.SubscribeOper`。功能与 V3 版本 v3.5.0 一致。

## 为什么需要

宿主的洗版（best_version）没有次数上限：只要某集的 `episode_priority` 还没到 100，每轮搜索到更高优先级的候选就会重新下载替换。于是同一集可能被「洗」很多次——先来个 1080p、再来个 4K、过几天又来个更高码率的 4K，每次都重下一遍。

本插件在宿主的**资源选择**环节介入，把「本批候选」按每集阶段收窄：

| 阶段 | 含义 | 本轮放行的候选 |
| --- | --- | --- |
| 0 | 该集还没有任何版本 | 本批优先级**最低**的那一档（首发不追高；订阅设了分辨率时只在该分辨率里取最低档） |
| 1 | 该集已有首发版本 | 只放行**本批最高档**，且必须严格高于首发档；本批没有更高档就全部拦掉 |
| 2 | 该集已升级完成 | 全部拦掉，并把该集写成 `episode_priority = 100` |

这样每集最多下载两次：首发一次、最终一次，**没有任何档位需要配置**。

## 判据：本批最高档，不预设形态

插件**不判断**杜比 / HDR / 10bit / HQ 这些形态谁高谁低——那没有客观答案。它只做两件事：

1. 首发取**本批最低档**：拿到出得最快的那版；
2. 最终取**本批最高档**：宿主只会把「严格高于已下档」的候选送进资源选择事件（`app/application/subscription/priority.py:get_best_version_interested_episodes`），所以本批最高档天然就是「现在能拿到的最好那版」。

高低由宿主的**规则组**决定：规则串用 `>` 分层，首层 `pri_order` 为 100、每层递减 1（`app/modules/filter/__init__.py:__get_order`），插件只比这个数字。

三种典型情形（规则组 `4K&DOLBY > 4K > 1080P`）：

| 实际发布顺序 | 插件行为 | 总下载次数 |
| --- | --- | --- |
| 杜比版最先出 | 首发就是最高档，没有更高档可升 | 1 |
| 1080p 先出，杜比后来 | 首发 1080p → 升到杜比版 → 封顶 | 2 |
| 1080p 先出，4K 标准版后来（没有杜比） | 首发 1080p → 升到 4K 标准版 → 封顶 | 2 |

**不会死等**：这一版没有更高档时宿主根本不发事件，插件零动作。没杜比的剧就停在首发那版，不会一直等一个可能永远不存在的版本。

两个配置前提：

- **规则组层数要兜住低档**，否则没命中任何层的种子会被宿主直接丢弃（`app/modules/filter/__init__.py:__filter_torrents`）——建议 `4K&DOLBY > 4K > 1080P`；
- **订阅侧用「分辨率 / 质量」表达可接受范围即可**，不建议设「特效」「包含关键词」：这两项是标题正则硬过滤（`app/application/torrent/download.py:_text_filter_failure`），设了之后首发档在宿主搜索阶段就被删掉，插件在资源选择环节看不到它，首发也就快不起来。

## 工作原理

1. 监听 `ChainEventType.ResourceSelection`（宿主在排序与下载之前发出，允许插件替换候选列表）
2. 只处理**来源是订阅**的批次：`origin` 形如 `Subscribe|{json}`，从里面取订阅 ID；手动搜索、RSS 等其它来源一律放行
3. 用订阅的 `episode_priority`（电视剧按集）或 `current_priority`（电影按整部）判断每集当前阶段
4. 按阶段算出「本轮允许的优先级」（阶段 0 取本批最低档、阶段 1 取本批最高档），只保留优先级等于它的候选，其余从本批里剔除
5. 升级完成的集写 `episode_priority = 100` 并重算 `current_priority`，宿主此后不再为它搜索

## 阶段靠对账，不靠记账

插件**不在选择候选时推进阶段**——选择不等于下载成功。阶段每次都用宿主自己维护的下载事实对账：

- 电视剧：宿主下载成功后写 `subscribe.episode_priority[集号] = max(旧值, pri_order)`
- 电影：宿主下载成功后写 `subscribe.current_priority = max(pri_order)`

所以下载失败（宿主没写库）时阶段原地不动，下一轮仍按原阶段重试；不会被永久卡死。写 `100` 之前的旧值会存进插件状态，随时可以用 `/restore` 还原。

## 配置说明

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| 启用插件 | 关 | 开启后监听资源选择事件 |
| 试运行（只记日志） | 开 | 只把将要放行/拦截的候选写进日志，不改候选、不写库 |
| 处理电视剧 | 开 | 按集计算阶段 |
| 处理电影 | 开 | 按整部计算阶段 |

没有档位相关的配置项：首发最低档、最终本批最高档、每集最多两次，都是固定的。

## 插件接口

| 接口 | 说明 |
| --- | --- |
| `GET /status` | 每订阅每集的阶段、首发优先级、升级目标与最近一轮处理摘要 |
| `POST /reset` | 清空插件状态（不动订阅表） |
| `POST /restore` | 把插件写过 `100` 的集还原成写之前的优先级 |

## 注意事项

- **只对洗版订阅收尾**：只有开启了洗版的订阅才会在第二次下载后写 `100`。没开洗版的订阅，宿主靠「缺失集」触发重下，永久拦截会让删掉的文件再也下不回来——这类订阅只做「首发最低档」，升级后一律放行
- **最终一次就封顶**：第二次下载完成后立即写 `100`，之后即使出现更高档也不再洗。想要更高画质，手动把该集的 `episode_priority` 改回去，或用 `/restore` 重来
- **首发要快就别在订阅里锁特效**：订阅的「特效」「包含关键词」是标题正则硬过滤，设了之后候选池里只剩那一类资源，首发也只能等它出
- **完全没配规则组时不洗第二轮**：所有候选 `pri_order` 都是 0，宿主判定不出「更高档」，插件自然不动作——此时行为等于「只下一次」
- **整包资源不参与档位筛选**：候选既没有 `allowed_episodes` 也没有 `episode_list`（拿不到集数信息）时原样放行，避免整包资源被误拦
- **覆盖不到目标集的候选会被丢弃**：例如集号落在订阅「开始集数」之外的候选，即使优先级匹配也会被剔除
- **写库范围最小**：只写 `episode_priority` 与 `current_priority`，其它集原有优先级保留
- **先试运行**：默认开启试运行，确认日志里的「保留 N 个 / 优先级」符合预期后再正式启用

## 安装

把本仓库配置为 MoviePilot V2 插件市场后，在插件市场中安装「洗版两次」。

    package.v2.json
